# F5: Performance & asset-pipeline upgrades

> Scope: cold start, image decode, animation cost, baseline profiles / R8 / delivery, 2026 Compose practices.
> Local-first (2026-09-11). Network (developer.android.com / WebSearch) was unreachable from this sandbox; every finding below is grounded in a local file quote. External-doc recommendations are labeled by confidence and not attributed to unread pages.

## Findings

### [1] Bundled res+assets weigh ~72.5MB; portraits alone are 50.5MB of oversized WebP, with no App Bundle packaging task
- quote: "PATH=...drawable-nodpi COUNT=62 BYTES=54242780 MB=51.73" / "char portraits: 31, bytes 52,968,070 (50.5 MB)" / "TOTAL assets+res: 72.5 MB"; largest file `char_ur_zhulong.webp` = 3,219 KB; avg portrait = 1,669 KB
- url: local measurement of `MilanKotlin/app/src/main/res/drawable-nodpi` + `assets/`; build only documents `:app:assembleDebug|assembleRelease` APK paths in `AGENTS.md`
- source_type: primary
- published: 2026-09-11 (measured)
- confidence: high
- **Cost**: install/download size and cold-start resource IO. `drawable-nodpi` does not density-split, so Play density splits will not shrink these files. Every portrait is still multi-megabyte even after WebP.
- **Upgrade**: (a) recompress portraits to target ≤400KB (or 1024-max-edge) offline; (b) ship `bundleRelease` (AAB) instead of fat APK; (c) consider `androidResources.noCompress` audit only after recompression; (d) drop packaging leftovers (see [2]).
- **Risk**: visual quality at Full/2x decode must be re-checked; keep source masters outside `src/main`.

### [2] Dead weight ships inside the package: `assets/data.json.bak` (122KB) and `drawable-nodpi/.bak/char_ur_zhulong.webp.20260906` (~3.6MB)
- quote: "data.json.bak 121,623 bytes" and "char_ur_zhulong.webp.20260906 3,583,690"
- url: `MilanKotlin/app/src/main/assets/data.json.bak`, `MilanKotlin/app/src/main/res/drawable-nodpi/.bak/`
- source_type: primary
- published: unknown
- confidence: high
- **Cost**: ~3.7MB of non-runtime bytes that may enter APK/AAB. aapt2 ignores some dotted dirs but `assets/**` is copied verbatim — `data.json.bak` is certain to package.
- **Upgrade**: move backups out of `src/main` (e.g. `tools/backup/`), add a packaging guard test or `androidComponents` filter.
- **Risk**: none if files stay in VCS outside source sets.

### [3] Two full CJK fonts (8.04MB) are bundled; Ma Shan Zheng is 5.59MB but only used for two ritual text styles
- quote: "ma_shan_zheng_regular.ttf 5.59 MB" / "noto_serif_sc_variable.ttf 2.45 MB"; Theme.kt: "楷书仅两处——「丹青录」Logo 与抽卡仪式标题"
- url: `MilanKotlin/app/src/main/res/font/`, `MilanKotlin/app/src/main/java/com/milan/game/ui/theme/Theme.kt` (BrandType/RitualType, MaShanZheng/NotoSerifSC)
- source_type: primary
- published: unknown
- confidence: high
- **Cost**: ~8MB of APK bytes plus first-use font parse on UI path when Brand/Ritual text composes (gacha reveal).
- **Upgrade**: subset MaShanZheng to the actual Brand/Ritual string set (fontTools `pyftsubset`); subset Noto Serif SC to used CJK + Latin, or use Downloadable Fonts for the display face. Keep variable-axis if needed.
- **Risk**: missing glyphs if future UI strings are added without re-subsetting; keep a CI charset check.

### [4] Baseline profile is a 72-line hand-written stub; generator “待接入” while profileinstaller 1.4.1 is already wired
- quote: "# 手写 Baseline Profile：冷启动关键路径… # 生成工具（macrobenchmark）待接入"; app/build.gradle.kts: "安装时注入 Baseline Profile（src/main/baseline-prof.txt），冷启动预编译热点" + `implementation(libs.androidx.profileinstaller)`
- url: `MilanKotlin/app/src/main/baseline-prof.txt`, `MilanKotlin/app/build.gradle.kts`, `MilanKotlin/gradle/libs.versions.toml` (`profileinstaller = "1.4.1"`)
- source_type: primary
- published: unknown
- confidence: high
- **Cost**: only a handful of app + Compose methods are HSPL-warmed; most first-frame Compose/UI/Material3/nav paths remain interpreter/JIT after install. Startup uplift from profileinstaller is largely unrealized.
- **Upgrade**: add `androidx.baselineprofile` Gradle plugin + `:baselineprofile` module; generate from a Macrobenchmark journey (cold start → Home → Gacha reveal → Character list). Keep the hand file only until the generated one replaces it.
- **Risk**: generated profiles bloat install slightly; regenerate whenever nav/compose BOM changes.

### [5] `:benchmark` measures a non-minified variant — `isMinifyEnabled` is only on `release`, not on `benchmark`
- quote: app/build.gradle.kts `release { isMinifyEnabled = true; isShrinkResources = true … }` vs `create("benchmark") { isDebuggable = false; signingConfig = …; matchingFallbacks += listOf("release") }` (no minify flags)
- url: `MilanKotlin/app/build.gradle.kts` lines 42–56
- source_type: primary
- published: unknown
- confidence: high
- **Cost**: StartupBenchmark numbers are not representative of production R8/shrinkResources builds (method count, class init, and startup path differ). `matchingFallbacks` only affects dependency variant selection, not the app module’s own R8.
- **Upgrade**: enable `isMinifyEnabled`/`isShrinkResources` on the `benchmark` buildType (or use `initWith(release)` + debug signing), and point Macrobenchmark at that variant.
- **Risk**: keep rules must cover benchmark runner; validate once with `:benchmark:benchmarkRelease` on device.

### [6] StartupBenchmark is a minimal smoke: no CompilationMode, no frame metrics, UI wait is brittle Chinese text, 5 iterations
- quote: "metrics = listOf(StartupTimingMetric()), iterations = 5" … "device.wait(Until.hasObject(By.text(\"次元裂缝\")), 5_000)"
- url: `MilanKotlin/benchmark/src/main/java/com/milan/game/benchmark/StartupBenchmark.kt`
- source_type: primary
- published: 2026-08-13 (comment date)
- confidence: high
- **Cost**: cannot attribute regressions to baseline-profile vs first-frame jank; string-based wait fails if copy changes (and already encodes a specific gacha CTA).
- **Upgrade**: set `startupMode = StartupMode.COLD`, add `CompilationMode` variants (None/Partial/BaselineProfile/Full), add `FrameTimingMetric` (or `TraceSectionMetric`) for Home + Gacha; replace text wait with resourceId/contentDescription or a stable navigation action.
- **Risk**: cold mode requires stopping the process between iterations; longer CI time.

### [7] Character list decodes `PortraitTarget.Full` (~0.95MB/bitmaps) inside LazyVerticalGrid — design doc had planned Thumb for cards
- quote: CharacterCard.kt: `target = PortraitTarget.Full` inside Lazy grid items; PortraitLoader.kt: "Full=2x / Thumb=4x"; design doc table: "CharacterListScreen ListCard 立绘框（58dp） | Thumb"
- url: `MilanKotlin/app/src/main/java/com/milan/game/ui/components/CharacterCard.kt:124-133`, `CharacterListScreen.kt:138-157`, `docs/superpowers/specs/2026-08-08-performance-optimization-design.md`
- source_type: primary
- published: 2026-08-08 (spec) / current code
- confidence: high
- **Cost**: grid scroll + shared-element path competes for the 24MB LRU; ~25 Full bitmaps fill the cache; decode bandwidth is 4× Thumb. Avatars already exist (1.2MB total) and are underused for list chips.
- **Upgrade**: list cards should use `PortraitTarget.Thumb` (or `Avatar` for tiny slots); reserve `Full` for detail/hero/reveal. Align CharacterCard with the already-chosen D2 tiers.
- **Risk**: shared-element transition quality if sizes diverge; verify visually.

### [8] `InkWashPortrait` rebuilds a `RadialGradient` shader and issues up to 900 `drawPoint` calls every draw; Home hero floats forever via infinite transition
- quote: PortraitImage.kt: "vignettePaint.shader = android.graphics.RadialGradient(...)" inside Canvas; "maxGrainPoints = 900"; HomeScreen.kt HeroPortrait: `rememberInfiniteTransition(label = "float")` … `infiniteRepeatable(tween(3000), RepeatMode.Reverse)`
- url: `MilanKotlin/app/src/main/java/com/milan/game/ui/components/PortraitImage.kt:291-342`; `HomeScreen.kt:330-361`
- source_type: primary
- published: unknown
- confidence: high
- **Cost**: every Home frame re-invalidates the hero PortraitImage, which re-runs ColorMatrix bitmap draw + new gradient object + grain loop. Multiplied by list screens that also call PortraitImage.
- **Upgrade**: hoist vignette shader to `drawWithCache` / `remember(size)`; bake grain+vignette into an offscreen bitmap once per (bitmap,size) or drop grain on Thumb; animate hero with `graphicsLayer { translationY }` without recomposing/drawing the filter path (layer still redraws, but shader allocation and grain can be cached); respect reduce-motion setting already present in tests.
- **Risk**: visual fidelity of ink filter; A/B screenshots required.

### [9] DamageFloatingText still measures text and builds strings every frame for every event (parallel stagger already fixed)
- quote: "val measured = textMeasurer.measure(text, style)" inside DrawScope; "buildString { append(\"-${event.damage}\") …}"; comment: "R7-P1：并行推进而非串行 delay+animateTo"
- url: `MilanKotlin/app/src/main/java/com/milan/game/ui/components/DamageFloatingText.kt:55-68, 107-153`
- source_type: primary
- published: 2026-09 (R7)
- confidence: high
- **Cost**: during a 30-strike battle log, each frame re-layouts N strings (compose text measure is non-trivial) and allocates; full-screen Canvas keeps the whole layer invalid.
- **Upgrade**: precompute `TextLayoutResult` (and color variants) once in `LaunchedEffect(events)` keyed by (damage, defeated, miss); draw with `drawText(precomputed)` + `graphicsLayer` for alpha/scale; consider a smaller overlay bounds.
- **Risk**: style must track theme/fontScale; cache key includes those.

### [10] Gacha idle stage keeps multiple `withFrameNanos` / `rememberInfiniteTransition` loops alive (Charge + Backdrop + Herald particles)
- quote: CyberCharge.kt: `while (isActive) { withFrameNanos { nano -> time = nano / 1_000_000_000f } }`; CyberStage InkWashBackdrop same pattern; CyberHerald: infinite spin 14s + pulse + `if (!testMode) InkParticles(...)`
- url: `MilanKotlin/app/src/main/java/com/milan/game/ui/gacha/CyberCharge.kt:35-40`, `CyberStage.kt:146-151, 231-313`
- source_type: primary
- published: unknown
- confidence: medium
- **Cost**: on Gacha tab, several full-screen (or 220dp) canvases redraw every frame even when the user is idle; 22–56 particles + rings + dust. Battery + thermal + chance of jank on low-end (the same devices the 2026-08-08 spec targeted).
- **Upgrade**: single shared time provider; pause loops when stage is not visible / when `LocalLifecycleOwner` is not RESUMED; gate particle density behind reduce-motion / low-end tier; move static grid/rings out of the per-frame path (`drawWithCache`).
- **Risk**: visual timing must stay deterministic for tests (`testMode` already freezes time).

### [11] Weapon art uses a separate 8-entry LruCache with no memory-pressure trim (unlike PortraitLoader)
- quote: WeaponPanel.kt: "private val WeaponArtCache = LruCache<String, Bitmap>(8)"; decode `inSampleSize = 2` from `assets/weapons/*.webp` (~380KB avg compressed)
- url: `MilanKotlin/app/src/main/java/com/milan/game/ui/characters/WeaponPanel.kt:141-167`
- source_type: primary
- published: unknown
- confidence: medium
- **Cost**: up to 8 × (512×512 ARGB ≈ 1MB) ≈ 8MB outside the PortraitLoader 24MB budget and not cleared on `onTrimMemory` (PortraitLoader is registered in MilanApp; this cache is not).
- **Upgrade**: share the PortraitLoader cache policy or register the same ComponentCallbacks2; size by `byteCount` not entry count; optionally move weapon WebP to drawable-nodpi only if density-independent (they already are assets).
- **Risk**: low.

### [12] Cold start already async-init’s GameState; remaining critical-path gaps are first-frame Compose, fonts, profile coverage, and packaging IO — not data.json parse
- quote: MilanApp.kt: "P3-11 启动性能：data.json（~50KB）读取/解析/enrich 与存档载入/sanitize 移出主线程冷启动关键路径"; measured `data.json` is actually **221.4KB**; Theme.kt R7-P0-1: "字号档位不在 Theme 读 AppGraph.service"
- url: `MilanKotlin/app/src/main/java/com/milan/game/MilanApp.kt:43-57`, `GameState.kt:39-92`, `Theme.kt:100-116`, measured asset size
- source_type: primary
- published: 2026-08 / 2026-09
- confidence: high
- **Cost**: comment under-states content size (~50KB vs 221KB). Init itself is off-main (good). Remaining startup = Application sync work (CrashReporter + MilanAudio.init) + MainActivity first composition + font/profile/cache warm-up + APK mmap of 50MB+ nodpi resources on first paint.
- **Upgrade**: keep async init; prioritize [3][4][5][6][1] for cold-start; optionally defer `MilanAudio.init`/SFX preload until after first frame (BGM already on HandlerThread). Re-measure with a fixed Macrobenchmark after profile generation.
- **Risk**: deferring audio must keep race-free playBgm (existing synchronized design).
